# 0002. 剪贴历史的本地存储

- 状态：已采纳
- 日期：2026-10-20

## 背景

剪贴历史需要跨重启持久化，默认保留 500 条（可选 100 / 500 / 1000 / 5000），单条超过 10 MB 不记录，重复内容移到最前而不新增。采集范围是纯文本、富文本、图片、文件四种原始类型，链接、颜色、邮箱是从文本派生的分类。粘贴时需要尽量还原原始格式（例如富文本）。

未来计划支持 iCloud 同步，且同步必须可选择：文件条目只是本机路径，不能同步到其他设备；用户也可能只想同步文本。

## 决策

- **使用 SwiftData**，库文件位于沙盒容器的 Application Support 下。
- **双模型**，参考 Maccy：
  - `HistoryItem`：一次复制，含稳定的 `UUID` 身份、来源应用、首次/最近复制时间、`updatedAt`、用于展示与搜索的 `title`（截断到 1000 字符并过滤会让 CoreText 卡死的字符）。
  - `HistoryItemContent`：剪贴板上的一种数据格式，`type`（UTI 字符串）+ `value: Data`，`value` 使用 `@Attribute(.externalStorage)` 外置大数据。
  - 回填时把一条记录的全部格式原样写回，展示类型由格式推导，不按类型分表。
- **存储层位于 `@MainActor`**，使用 `mainContext`；`ModelContainer` 由 `AppDelegate` 装配并通过构造参数注入，测试使用 `ModelConfiguration(isStoredInMemoryOnly: true)`。视图拿到的是存储层提供的数据，不直接持有 `ModelContext`。
- **按 CloudKit 约束建模**，为未来同步留路：不使用 `@Attribute(.unique)`（去重在存储层代码中完成），所有属性可选或带默认值，关系可选。
- **去重**：忽略临时性格式后，内容相同即视为同一条，移到最前并更新时间。
- **数据库无法打开时**：把损坏的库文件改名备份后新建，并提示用户，不 `fatalError`。
- **未来同步使用 `CKSyncEngine`**，而不是 SwiftData 自带的 CloudKit 自动同步，以便按记录挑选上传内容和控制冲突合并。

## 备选方案

- **系统 SQLite（`import SQLite3`）**：完全可控，可用 FTS5，但需要自写封装与迁移，代码量约翻倍；5000 条以内内存子串搜索已足够。放弃。
- **GRDB**：体验最好，但引入第三方依赖，收益不足以抵消。放弃。
- **按类型建模（文本表、图片表……）**：无法无损保留一次复制里的多种格式，新增类型需改结构。放弃。
- **`@ModelActor` 后台存储**：数据量小，收益不足以抵消 Swift 6 严格并发下的复杂度。放弃，必要时再迁移。
- **SwiftData + CloudKit 自动同步**：一个开关即可，但无法排除文件条目、无法按用户偏好挑选内容，且难以排查和测试。放弃。

## 后果

- 存储层是唯一接触 SwiftData 的地方，将来更换存储实现的影响范围限于此。
- 不能依赖数据库唯一约束，去重正确性完全由存储层测试保证。
- 所有读写在主线程进行，单条大数据的解码（如图片缩略图）需避免阻塞主线程。
