# 0006. 收藏夹的模型与淘汰语义

- 状态：已采纳
- 日期：2026-10-22

## 背景

剪贴历史按 `lastCopiedAt` 倒序、按保留条数上限从最旧的开始淘汰（见 ADR 0002）。用户需要把少数条目长期留住并归到「工作」「生活」这类自定义分组里，所以收藏不能只是一层展示筛选：

1. **收藏必须改变淘汰行为**。否则用户收藏的条目会在达到条数上限后按时间被静默删除，收藏夹会自己漏空。
2. **收藏必须有独立的排序时间**。若沿用 `lastCopiedAt`，用户重新复制一次已收藏的内容，该条会在收藏夹里跳到最前，把整理好的顺序慢慢打乱。
3. **分组本身是可增删的用户数据**。预设分组可被删除，删除分组不应连带删除剪贴内容。

## 决策

- **新增 `FavoriteTab` @Model**：`id`、`name`、`order`、`createdAt`，全部带默认值、无唯一约束，遵守 ADR 0002 的 CloudKit 兼容建模约束。
- **收藏关系挂在 `HistoryItem` 上**：`favoriteTab: FavoriteTab?` + `favoritedAt: Date?`。一条剪贴最多属于一个分组，用可选关系表达「未收藏」，用 `favoritedAt` 表达收藏顺序。
- **`enforceLimit` 只淘汰未收藏条目**：收藏条目不占用保留条数，也不被淘汰。收藏夹因此可以超出条数上限继续增长。
- **`clearAll` 只清未收藏条目**：「删除全部」是批量清理历史，不是删除用户主动保留的内容。
- **删除分组时把 `favoriteTab` 置 nil**，条目退回普通历史。不使用 `.cascade`：级联会删掉剪贴内容本身。
- **预设「工作」「生活」只在首次启动播种一次**，写入的是普通 `FavoriteTab` 记录，之后与用户新建的分组完全平等，可删除且不会重建。
- **分组与收藏关系都通过 `ClipboardHistoryStore` 读写**，视图不直接接触 `ModelContext`，与 ADR 0002 一致。
- **收藏内容可脱离剪贴来源手动创建**：主窗口收藏夹提供「添加文本…」，`ClipboardHistoryStore.addFavoriteText` 用与复制来源相同的 `HistoryItem`（`string` 内容）插入并直接挂到指定分组。它复用同一套去重、收藏时间与淘汰语义（收藏项不被淘汰），因此手动条目与复制来源在数据模型上没有区分；去重以「同一分组内相同内容」为准，不同分组可各自保留一条。

## 备选方案

- **多对多（一条剪贴可属于多个分组）**：能表达「同一条内容既是工作资料也是生活资料」，但「取消收藏」只能退化为「从当前分组移除」，用户会在别的分组里继续看到它；同一条还会在「全部」里重复出现。放弃。
- **`tabName` 字符串或 `tabID` + UserDefaults**：免迁移，但分组顺序、重命名与引用完整性都要在代码里手工维护，删除分组后还会留下悬空引用，且无法可靠地按分组查询。放弃。
- **收藏只做标记、不改淘汰**：实现最小，但收藏被静默删除是缺陷而非设计。放弃。
- **拖动排序**：需要额外的 `order` 持久化与拖拽交互，且与「重新收藏」的语义要重新定义，超出当前需求。`FavoriteTab.order` 已预留，暂只用于新建分组的追加顺序。

## 后果

- 收藏夹的总条数不再受历史保留条数约束，存储占用的上限因此不再由单一开关决定；设置页的「占用空间」仍是观察入口。
- 「删除全部」不再是「清空一切」：用户清完历史后收藏夹仍在，这是行为变更，需要在界面文案与发布说明里写明。
- `HistoryItem` 与 `FavoriteTab` 都参与同步边界时，收藏关系会随条目一起同步；文件条目的本地路径问题（ADR 0002）同样适用于收藏。
